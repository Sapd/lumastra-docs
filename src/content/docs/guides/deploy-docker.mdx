This page continues the [Quick Start](/start/quick-start/). It covers what you do once
Lumastra runs on a single host: a home server, a NAS or one VM. To run several web
replicas, use [Kubernetes](/guides/deploy-kubernetes/).

## 1. Set your public address

Use the address people type in the browser. Replace the example, then restart.

```bash
sed -i.bak 's|^# ORIGIN=.*|ORIGIN=https://media.example.com|' .env && rm -f .env.bak
docker compose up -d
```

`grep '^ORIGIN' .env` should print your address. Sign-in fails with a `403` when `ORIGIN`
and the browser address differ.

## 2. Put a reverse proxy in front

Follow the [Reverse proxy guide](/guides/reverse-proxy/) for Caddy, nginx or Traefik. If
the proxy runs in the same compose file, also delete the `ports:` block of the
`lumastra` service so nothing bypasses it.

## 3. Check that everything is healthy

```bash
docker compose ps
docker compose logs --tail 50 lumastra lumastra-worker
```

All services should show `healthy`. Right after a start, the `lumastra` log contains
`Schema migration completed successfully`. **Admin → System → Health** shows the state
of each part too.

## 4. Back up

Back up the PostgreSQL database, the `config` volume and `LUMASTRA_MASTER_KEY`. The
commands are in [Backup & recovery](/guides/backup-recovery/).

## 5. Update

Check the [release notes](https://github.com/Sapd/lumastra/releases) first. Then set the
new version and restart:

```bash
NEW=0.1.5   # example: use the release you want
sed -i.bak "s|lumastra:[0-9.]*|lumastra:$NEW|" docker-compose.yml && rm -f docker-compose.yml.bak
docker compose pull
docker compose up -d
```

The app runs its database migrations on start. Admins see a newer release in the bell
icon. For updates without dropped streams, see
[Zero-downtime updates](/guides/zero-downtime-updates/).

## What runs

| Service | Image | Role |
| --- | --- | --- |
| `lumastra` | `ghcr.io/lumastra/lumastra` | Web UI, API and playback |
| `lumastra-worker` | same | Library scans, metadata and other background jobs. Run exactly one. |
| `lumastra-postgres` | `pgvector/pgvector:pg18` | The database |
| `lumastra-valkey` | `valkey/valkey:9-alpine` | Job queue and locks. Never evicts, saves to disk. |
| `lumastra-valkey-cache` | `valkey/valkey:9-alpine` | Disposable cache |

Image tags: a version such as `0.1.4`, `stable` (the newest release), `beta` (the newest
release candidate) and `edge` (every commit to `main`, amd64 only, for testing). Why
there are several containers is explained in the [architecture overview](/architecture/overview/).

| Volume | Holds |
| --- | --- |
| `lumastra_postgres_data` | The database |
| `lumastra_valkey_data` | The job queue |
| `config` | Settings, `master.key`, artwork. Shared by web and worker. |
| `cache` | Image cache |
| `ffmpeg-cache` | FFmpeg binaries, downloaded on the first start |
| `plugins` | Installed plugins |

Mount your media into the web and the worker container at the same path: the worker
scans the files and the web container plays them.

## Reverse proxy & TLS

Lumastra speaks plain HTTP on port 3000. The [Reverse proxy guide](/guides/reverse-proxy/)
explains `ORIGIN`, `TRUSTED_PROXY_IPS`, compression, access logs and upload limits.

## Optional services

**Live TV proxy.** Add these lines to `.env`, then start the profile. Enable Live TV in
**Admin → Settings**. More in the [Live TV guide](/guides/live-tv/).

```dotenv
STREAM_PROXY_URL=http://lumastra-proxy:3000
STREAM_PROXY_SECRET=<openssl rand -hex 24>
```

```bash
docker compose --profile livetv-proxy up -d
```

## Sonic embedder sidecar

The sidecar powers sound-based music features. It is amd64 only. The image
`ghcr.io/lumastra/lumastra-sonic-embedder` is defined in the example file behind the
`sonic` profile.

1. Mount your media into `lumastra-sonic-embedder` at the same container path as on
   `lumastra`. Step 3 of the Quick Start did this already if you used its command.
2. Pick a password and set it as `SONIC_READER_PASSWORD` in `.env`. After the first start,
   create the read-only role:

   ```bash
   docker compose exec lumastra-postgres psql -U lumastra -d lumastra -c "
     CREATE ROLE sonic_reader LOGIN PASSWORD '<same password>';
     GRANT CONNECT ON DATABASE lumastra TO sonic_reader;
     GRANT USAGE ON SCHEMA public TO sonic_reader;
     GRANT SELECT ON media_audio_embeddings TO sonic_reader;"
   ```

3. Uncomment `SONIC_EMBEDDER_URL` on `lumastra` and `lumastra-worker`.
4. Start it:

   ```bash
   docker compose --profile sonic up -d
   ```

The sidecar sizes itself from its memory limit. Use `3g` for a small NAS, `6g` (the
default) for a home server and `10g` or more for a large library. Keep
`SONIC_EMBEDDER_THREADS` at or below its `cpus` limit. A track that does not fit fails
with `Sonic sidecar memory too small`: raise the limit and retry the failed items. The
features are switched on in [Music discovery](/guides/music-discovery/).

## If something differs

**Your install is older than the dedicated worker.** Older installs ran one container for
web and jobs, with one Valkey. Current versions need a separate worker and a second
Valkey, and refuse to start without them (`TASK_CACHE_URL is required`).

### Upgrading to the dedicated worker and two Valkeys

Your existing Valkey becomes the task Valkey and keeps its queue. Do not just add
`--appendonly yes` and restart: a Valkey that only has snapshots then starts empty.

1. Back up the database and `LUMASTRA_MASTER_KEY`.
2. Switch the running Valkey to AOF first, and wait until the rewrite is done:

   ```bash
   set -a; . ./.env; set +a
   VK="docker compose exec -e REDISCLI_AUTH=$CACHE_PASSWORD lumastra-valkey valkey-cli"
   $VK CONFIG SET appendonly yes
   $VK CONFIG SET maxmemory-policy noeviction
   $VK INFO persistence | grep -E 'aof_rewrite_in_progress|aof_last_bgrewrite_status'
   ```

   Repeat the last command until you see `aof_rewrite_in_progress:0` and
   `aof_last_bgrewrite_status:ok`.
3. Compare your file with the [current example](https://github.com/Sapd/lumastra/blob/v0.1.4/docker-compose.example.yml).
   Add the cache Valkey and the worker service. Give the existing Valkey the flags
   `--maxmemory-policy noeviction --appendonly yes --appendfsync everysec`. Remove
   `WORKER_MODE` and `DEDICATED_WORKER` from the web service. Set `CACHE_URL` to the new
   Valkey and `TASK_CACHE_URL` to the old one. Keep the old database number, usually `/0`.
4. Apply it with `docker compose pull && docker compose up -d`.
5. In **Admin → Tasks**, the jobs queued before the upgrade should start running.

Startup refuses to run when the task Valkey is empty but PostgreSQL still shows work in
flight, or when its eviction policy is not `noeviction`. Never point `CACHE_URL` and
`TASK_CACHE_URL` at the same Valkey.

**Valkey logs `Memory overcommit must be enabled`.** You can ignore it. To silence it, run
`sudo sysctl vm.overcommit_memory=1` on the Docker host.

**Your media is on NFS.** Mount options change scan speed a lot. See
[Performance tuning](/guides/performance-tuning/#nfs-mount-options-media-library).

**The host has no internet.** Set `FFMPEG_AUTO_DOWNLOAD=false` and point `FFMPEG_PATH` and
`FFPROBE_PATH` at your own binaries. See [What Lumastra sends where](/reference/data-flows/).

**You want to limit what a compromised container could reach.** The example file drops all
capabilities and mounts media read-only, but `:ro` only stops writes through that mount.
Export the media share read-only on the NAS too, and use host firewall rules (the
`DOCKER-USER` chain) for internal services Lumastra must not reach.

**Security fixes.** They appear as
[GitHub Security Advisories](https://github.com/Sapd/lumastra/security/advisories). Admins
see a red notice until the fixed release is installed.

**You want hardware transcoding.** See [GPU transcoding](/guides/gpu-transcoding/).

**Another stack on the same Docker network uses `lumastra-postgres` or `lumastra-valkey`.**
Docker DNS then resolves to the wrong container. Give Lumastra its own network.

**You need hard memory limits.** Add `mem_limit` and `pids_limit` per service, after you
measure peak use during a transcode and a library scan. Plan for about 1 GB for the
database and 2 to 4 GB for the worker.

**You want more than one web replica.** Use [Kubernetes](/guides/deploy-kubernetes/).
